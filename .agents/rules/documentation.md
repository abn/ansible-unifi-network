# Documentation rules

Extends `AGENTS.md`. Applies to `docs/`, module `DOCUMENTATION`, and changelog
fragments.

## Two documentation systems, both real

| Surface | Tool | Audience |
|---|---|---|
| `docs/` as an OKF v0.2 bundle | `okf validate docs/` | contributors and maintainers |
| `docs/docsite/` and module `DOCUMENTATION` | `antsibull-docs` | users of the collection |

They coexist under `docs/` without conflict. Module `DOCUMENTATION` is the source
of truth for reference material; the OKF bundle holds design, architecture and
contributor knowledge. Do not duplicate reference content between them.

## OKF bundle rules

- The bundle root is `docs/index.md` and carries **only** `okf_version` in its
  frontmatter. No other keys, and no `type`.
- Only the root may carry frontmatter. A per-directory `index.md` is navigation
  only.
- Every non-reserved concept file needs a non-empty `type` (`Overview`,
  `Reference`, `Guide`, `Decision`, `ADR`, `Log`), and should carry `title`,
  `description`, `status` and `tags`.
- `status` is one of `draft`, `stable`, `deprecated`. `active` is not valid OKF
  and the validator will say so.
- `docs/log.md` records **knowledge-base evolution only**: pages added, pages
  deprecated, structural refactors. It is not a changelog. Release notes come
  from `CHANGELOG.md`, generated by `antsibull-changelog` from
  `changelogs/fragments/`.
- `log.md` date headings must be ISO 8601 `YYYY-MM-DD`. A heading reading
  "Unreleased" fails validation.
- Links are relative or bundle-absolute. Never `file://` URIs, never absolute host
  paths.
- Every page passes the editorial invariants: no em dashes or en dashes, no
  internal hostnames, IPs or home paths, no task identifiers.

## An undecided design is documented as undecided

A documentation bundle that describes more than the code does is worse than one
that describes less: a reader designs against it and the code does not match.

- Say "not designed", "undecided" or "the model is the sibling collection" rather
  than writing a specification and hoping it holds.
- Name the pages the collection owes its users instead of writing them as stubs.
  A stub drifts from the code and there is nothing to catch the drift.
- Where a design is settled enough to record, record the *reason* and link to the
  ADR. The reasoning is the durable part; the shape will change.

## Module documentation

- `DOCUMENTATION`, `EXAMPLES` and `RETURN` are `r'''...'''` string literals.
  `validate-modules` cross-checks the argument spec against them, so a mismatch is
  a build failure, not a doc bug.
- Option descriptions are full sentences. Do not repeat the default in prose; the
  `default` key is checked against the code.
- Never list `check_mode` or `diff` information under `notes:`. It belongs in
  `attributes:`.
- Prefer `seealso` over `notes` for references, using the
  `- ref:` / `- module:` / `- name:` forms.
- Shared option blocks live in `plugins/doc_fragments/` and are pulled in with
  `extends_documentation_fragment` by FQCN. The collection needs its own
  attributes fragment: `ansible.builtin.action_common_attributes` supplies
  descriptions but not the `support` values that `validate-modules` cross-checks.
- Every new module ships an `EXAMPLES` block that matches what the integration
  tests actually run.
- A credential option's example reads `unifi_password: "{{ unifi_password }}"`, not
  a literal. Documentation is public-ready content and is read by people who copy
  from it.

## What the collection will owe its users

Not yet written, and named in `overview.md` so the gap is visible. Each needs a
module to be true of.

- **A first run**, and what a second run reports.
- **A credential table**, which for a controller means a username and password or
  an API key, and which deployment each works against.
- **A safety model**, covering the read-modify-write surface and what check mode
  does not tell you. A per-object override written from a stale read silently
  discards a concurrent console edit, and that sentence has to be somewhere.
- **A troubleshooting page** keyed to the failures the controller actually returns,
  which means measuring them, and which cannot be written from memory.

## Editorial

- No em dashes or en dashes. Use a hyphen, a colon, or restructure the sentence.
- No marketing prose. Say what the thing does and what it costs.
- No restating the code in comments or prose. Delete the duplication instead.
- No file-by-file enumerations in comments or docs. They rot the moment a file
  moves.
- Code fences are tagged with a language.
